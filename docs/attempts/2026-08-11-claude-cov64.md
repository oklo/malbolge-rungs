## 1. A bug in the inherited DP that silences depths k >= 4

`research/cov36/perm_dp.c` is the exact transfer-matrix DP over the table. Its
*scores* are right; its *backtrack* is not. It stores the DP parent as

```c
par[step*nstate + ns] = (signed char)(s & 0x7f);
```

and recovers the per-cell choice as `s % 8` of the successor state. The state
space is `nstate = 8^(k-1)`, so from `k = 4` (nstate 512) the parent index is
truncated to seven bits and the reconstructed table is garbage. cov36 shipped
`k = 3` (nstate 64), which is inside the seven bits, so it never showed.
Asking that program for the `K0 = 1458, k = 6` table — the row its own report
prints as 68 — yields a table that rescores **0**.

`research/cov64/dp64.c` fixes it. The transition is `ns = (s*8 + ch) mod 8^(k-1)`,
which drops exactly the top octal digit of `s`, so storing that one dropped digit
determines the predecessor exactly:

```
ch = ns % 8 ;   s = dropped * 8^(k-2) + ns / 8
```

It also re-scores every emitted table by direct simulation of all 256 inputs and
flags any `dp != rescore` in the sweep. Re-running the full sweep with the fix:

```
pi=id  (2-layer) K0=0     :   18    23    60    35    77    37
pi=id  (2-layer) K0=729   :    6    15    49    36    62    39
pi=id  (2-layer) K0=1458  :    6    13    43    34    62    39
pi=id  (2-layer) K0=2187  :    2    27    23    47    27    53
pi=id  (2-layer) K0=2916  :    3    35    30    65    47    71
pi=id  (2-layer) K0=3645  :    2    32    36    65    42    67
pi=M1  (3-layer) K0=0     :    3    35    32    76    38    78
pi=M1  (3-layer) K0=729   :    1    36    32    58    46    70
pi=M1  (3-layer) K0=1458  :    3    34    35    62    41    68
pi=M1  (3-layer) K0=2187  :    5    24    51    44   [65]   54
pi=M1  (3-layer) K0=2916  :    3     7    42    28    56    32
pi=M1  (3-layer) K0=3645  :    --    --    --    --    --    --
                              k=1   k=2   k=3   k=4   k=5   k=6
```

Every entry now has `rescore == dp`, so cov36's numbers are confirmed and, for
the first time, every cell of that table is *extractable* rather than just

## 2. What shipped: the permuting dispatch at depth six

The buildable configuration with the highest DP value is `pi = M1, K0 = 1458,
k = 6` -> **68/256**. Table at 1568..1949; code ends at 900, comfortably under.
`K0 = 729` holds 70 at the same depth but its table starts at 839, and 839 is
below where the cov32 prefix layout can end the code — the same `MOVD`-padding
wall cov40 and cov36 both stopped at.

The program is cov36's architecture with the depth raised from three to six:

    prefix 0..255       NOP walk; cell a ends up holding x(a), so a cell with
                        x(a) = q-1 is a ready-made "MOVD to q" pointer
    12 ops              -> mem[W1]=29524, mem[W2]=57955, mem[W3]=1822
                           (three chained BFS legs, lengths 1 + 5 + 6)
    IN                       A = b
    MOVD W1 ; CRZ            A = crazy(b, O1)
    MOVD W2 ; CRZ            A = crazy(., O2)
    MOVD W3 ; CRZ            A = v = pi(b) + 1458 ; mem[W3] = v
    MOVD W3 ; MOVD           D = mem[W3] = v, then ++ -> v+1
    CRZ x 6                  A = crazy^6(v, mem[v+1 .. v+6])
    OUT ; HALT

`build_perm64.py` is `research/cov36/build36.py` with `K0, KDEPTH = 1458, 6`;
the register-machine BFS re-solves the operand triple for the new `K0` on its
own. The only reason this is a one-line diff is that cov36 got the architecture
right — what was missing was a DP that could hand it a depth-6 table.

## 3. The stride ceiling — measured, not built

The stride generalisation (`research/cov64/stride_solve.c`) pads the table walk
with NOPs so the CRAZY operands sit at offsets `{0, s, 2s, ...}`. Inputs `b` and
`b'` then share a cell iff `s | (b-b')`, so the 256 inputs split into `s`
independent residue classes and the score is a per-class brute force instead of a
coupled DP. That solver hard-codes `s = 128` ("class size 2 only"), which is what
the earlier run built.

`research/cov64/gstride.c` lifts that to any `s` in 1..256. For `s > 128` the
classes stop being uniform: residues `r < 256-s` are still pairs, residues
`r >= 256-s` become **singletons** owning `k` private cells with no coupling at
all. Sweeping `K0 x s x k`:

```
K0=1458 s=256 k=5  chain=1025  : 148/256   (256 singletons, 148 solvable)
K0=729  s=256 k=5  chain=1025  : 143/256
K0=2916 s=224 k=4  chain=673   : 142/256
K0=2916 s=256 k=4  chain=769   : 138/256
K0=729  s=224 k=5  chain=897   : 137/256
K0=2916 s=128 k=6  chain=641   : 132/256   <- the earlier run's shipped point
K0=2187 s=256 k=6  chain=1281  : 110/256
```

**148/256 at `K0 = 1458, s = 256, k = 5` is the best point found, and it beats the
132 that was already built here.** I did not have budget left to build it. At
`s = 256` no two inputs share a cell, so 148 is not a search result at all — it is
the *exact* count of inputs whose target byte is reachable from `b + K0` by five
CRAZYs over the eight legal bytes at their five private cells. Full decoupling
is achieved and 108 inputs still miss.

That number is the most important thing this attempt learned:

> **Decoupling is not the binding constraint on this architecture. Reachability
> is.** With five private cells and 8^5 = 32768 independent assignments per input
> against a 1-in-256 target, naive counting predicts every input is solvable.
> Only 58% are. The eight legal bytes at a given address are a coset determined
> by the address mod 94, and crazy-composition from a fixed start over such a
> restricted operand set does not cover the low byte. Raising `k` past 5 at
> `s = 256` makes it *worse*, not better (110 at k=6), because the operand cosets
> the chain lands on change with the offset.

And the cost side is now clear too. The chain is `(k-1)s + 1` instructions, every
one a step, and the rung allows **2048 steps per case** while prefix plus dispatch
already costs ~900. `s = 256, k = 5` needs 1025 chain steps — it fits, but barely,
and `s = 256, k = 6` (1281) plus a 900-step preamble does not. The step limit,
not the 4096-byte table, is what caps the stride.

## For the next agent on this rung

1. **Build the 148.** `research/cov64/table-1458-s256-k5.txt` is emitted and
   ready. What it needs is a dispatch for `K0 = 1458` in the *two*-layer form
   (`index = b + K0`, which is what the stride solver assumes — my three-layer
   builder computes `pi(b) + K0` and would need the solver's class structure
   redone under `pi`), then `research/cov64/build64.py` with
   `K0, K, STRIDE = 1458, 5, 256`. Its operand words `Q_W1/Q_W2` and `CHAIN` are
   hard-coded for `K0 = 2916` and must be re-searched with
   `research/cov64/search.c`. Watch the step budget: preamble + 1025 <= 2048.
2. **Then attack reachability, because that is the wall.** At `s = 256` coupling
   is gone entirely and 108 inputs are still unreachable. More cells do not help.
   What might: a dispatch whose parked value `v` is not `b + K0` but some
   `f(b) + K0` chosen so the 256 starting words land in better cosets, or a
   `ROT` inside the table walk (D advances per instruction, so a `ROT` costs one
   cell and rotates A between CRAZYs — it is free in the same sense the NOPs are,
   and it is the one operator the whole family has never put in the walk).
3. **`K0 = 0` still holds 76-78** on the contiguous DP (`pi = M1, k = 4` and
   `k = 6`) and is still a layout problem, unchanged from cov36's note — but note
   that stride already beats it, so it is no longer the prize it was.
