## Construction

The first probe ran the map7b winner against map8. It passed seven cases, but
both `0xa7` and `0xc0` reached the same post-dispatch state and emitted `0x91`.
Because their accumulator, code pointer, data pointer, and mutated memory were
identical at that point, a tail-only repair could not distinguish the lanes.

The search therefore enumerated the repository's 39 eight-way-separating
CRAZY preludes and reused the map7b two-stage architecture:

1. CRAZY dispatch maps each input to a landing address.
2. A lane walks from its landing to a shared or split `MOVD,JUMP` station.
3. Its walk distance gives it a lane-specific data pointer.
4. That pointer selects a private second jump and a short output tail.
5. Joint byte-assignment backtracking rejects source-cell collisions, and the
   full diagnostic VM executes every complete layout before native checking.

A zero-split pass used a nominal 60,000-node budget on each of all 39
separating configurations. Every lane had legal individual tail plans, but no
configuration produced a complete joint byte assignment. The next stratum
allowed exactly one cluster split with a nominal 20,000-node budget per
geometry. Configuration 11 succeeded at split mask 6:

- CRAZY positions: `3, 4, 7, 9`
- legal operand bytes: `113, 37, 86, 68`
- landings: `02→55`, `06→56`, `a7→58`, `c0→59`, `09→65`, `30→68`,
  `6f→140`, `82→149`
- stations: the six low lanes share address 70; `6f` uses 148; `82` uses 158
- `a7→f6` and `82→d3` use ROT-bearing tails

The checked-in search reproduces the winning artifact. Build the debug native
binary first, then run the winning worker/config slice:

```sh
cargo build -p harness
python3 research/map8_search.py 3 8 1 20000 1 11 1
```

The search writes candidates under the platform temporary directory
(`malbolge-rungs-map8/`) and natively checks all eight inputs before reporting
success.

## Framework synopsis

The strongest part of MAL-51 is adjudication: the rung is frozen, the native VM
is deterministic, every case starts fresh, limits are explicit, and a solved
leaderboard entry must ship an executable artifact that CI re-verifies. The
map8 claim is consequently much stronger than a prose or self-reported result.

The attempt also exposed several shortcomings for benchmarking frontier models
and agentic harnesses:

1. **No standard run manifest.** The solution schema records a free-form solver
   object but not a required model id/version, harness version, prompt or policy
   hash, repository commit, tool permissions, machine, concurrency, token use,
   wall time, CPU time, or candidate/evaluator-call count. This runtime did not
   expose its exact model version, forcing the model field to remain null. That
   prevents apples-to-apples harness comparisons even though correctness is
   comparable.

2. **The leaderboard records winners, not attempts.** There is no machine-
   readable attempt schema for budgets, intermediate scores, negative results,
   traces, or termination reasons. Unsuccessful runs disappear, creating
   survivorship bias and making sample efficiency impossible to estimate.

3. **Construction provenance had drifted out of the repository.** The map6,
   map7a, and map7b records describe generator searches, but their actual
   builders were not checked in. This attempt had to recover the map7 scripts
   from a temporary work directory before adapting them. The map8 search is now
   included, but earlier frontier results remain artifact-reproducible rather
   than method-reproducible.

4. **Dispatch feasibility is too shallow to price synthesis difficulty.** Its
   count of distinct landing configurations correctly orders some rungs, but
   all 39 map8 preludes separate the inputs while the entire bounded zero-split
   pass found no composable layout. The estimator ignores station placement,
   source-cell aliasing, legal tail availability, and path-dependent mutation.
   A second metric based on joint lane compatibility would be more predictive.

5. **Finite-map epoch counts are cosmetic.** The submission instructions ask
   for `--epochs 5`, while finite-map and coverage cases are seed-independent.
   Reporting `8/8 × 5 epochs` looks stronger but executes the same cases five
   times. The CLI or leaderboard should label these as repeated confirmations,
   or normalize them to one definitive epoch.

6. **Artifact identity mixes raw and canonical programs.** The evaluator strips
   ASCII whitespace before enforcing length, while the site hashes and reports
   the raw file. A normal trailing newline therefore makes this artifact
   simultaneously “161 bytes” on the site and “160 bytes” to the judge, with
   two reasonable SHA-256 identities. The verifier output should expose both
   explicitly, or the repository should require canonical source files.

7. **The public ladder is not an uncontaminated benchmark by itself.** Published
   instances, solutions, and architectural notes are intentionally reusable.
   That is excellent for an open research ladder but measures tool use and
   transfer as much as novel reasoning. Procedural instances help, but the repo
   does not specify a sealed evaluation protocol that prevents a filesystem-
   capable agent from reading held-out rung files or seeds. A benchmark service
   or explicit orchestrator boundary is needed for credible blind evaluation.

8. **Human-maintained summaries drift.** At the start of this attempt, the JSON
   leaderboard contained solved map7a/map7b records while the README snapshot
   stopped at map6 and still called map8+ open. The static site is generated
   from canonical data, but duplicated prose is not. Generated README tables or
   a single-source policy would avoid this inconsistency.

These gaps do not weaken the map8 correctness result. They limit what can be
inferred from it about model quality, harness quality, or search efficiency—the
dimensions the proposed benchmark ultimately wants to compare.
