## The wall this rung was supposed to be behind

cov32 proved by exhaustive enumeration that **34/256 is the exact ceiling of the
whole branchless CRAZY/ROTATE family**, and cov34 realised that optimum. The
cov34 report drew the obvious conclusion:

> cov36 is a genuine wall, not a budget problem, for this entire approach. […]
> Ranks 18–21 (cov36/40/48/64) are all on the far side of that same single wall
> and are probably not meaningfully ordered relative to each other by difficulty
> — they are one problem, not four.

The first half is right: 34 is a proof, and no straight-line program beats it.
The second half is wrong, and this attempt is the counterexample. The branch that
gets past 34 is not the lane/dispatch architecture that stalled at 27/256 on the
finite-map rungs. It is much cheaper, and it costs **four instructions**.

## The mechanism: make the dispatch value equal the input

Malbolge's `MOVD` (`j`) sets `D = mem[D]`, then `D` is incremented at end of
cycle. So if a cell holds a value `v`, one `MOVD` on that cell leaves `D = v+1`:
the *data* pointer becomes an arbitrary computed address. The following `CRAZY`
then reads whatever byte the program has at that address. That is an
input-dependent branch, and unlike a control branch it needs no code duplication.

The prior cov36 research in `research/cov36/` (`branchgain.c`, `classlayer.c`,
`minimal.c`) modelled this correctly but asked for **a few classes**: split the
inputs by one trit and give each class its own operand. That is the expensive
version — every class needs its own prepared word, and `classlayer.c`'s operands
are forced to be prefix bytes, whose trits 6..9 are all zero, so the classes'
constants are linked rather than free.

The cheap version is the opposite extreme. Take the dispatch map to be the
**identity** on trits 0..5:

    A = crazy(crazy(b, O1), O2)      with trits 0..5 of O1 and O2 both = 1

`M1 ∘ M1` is the identity (M1 = (1,0,2) is an involution), so positions 0..5 of
the result are `b`'s own trits. Choosing the high trits of the two operands to
compose to the constant map `2` at position 6 and `0` at positions 7..9 gives

    A = v = b + 1458      (1458 = 2·3^6)

and the second `CRAZY` parks `v` in the cell it wrote. One `MOVD` on that cell
sets `D = v + 1 = b + 1459`.

**The input is now the table index.** There are 256 classes, one per input, and
none of them cost anything to separate — no per-class construction, no pointer
pool, no layout search. The two operands are

    O1 trits = [1,1,1,1,1,1,0,1,1,1] = 28795
    O2 trits = [1,1,1,1,1,1,2,1,1,1] = 30253

## Where the table comes from: the program's own bytes

The table lives at addresses 1459..1716, past the code, and is never executed —
the program halts at 1433. Those bytes are part of the source, so they cost
nothing to build, but Malbolge source validity constrains them: the byte at
address `a` must satisfy `(byte + a) mod 94 ∈ {4,5,23,39,40,62,68,81}`, which
leaves **exactly eight legal values per cell**.

The tail is three `CRAZY` layers reading `mem[b+1459]`, `mem[b+1460]`,
`mem[b+1461]`. Consecutive inputs therefore share table cells, so the choices are
coupled — but only along a chain, three cells wide. The exact optimum is a
transfer-matrix DP over 8² states, which is what `table_dp.c` computes. Over the
five reachable table offsets and depths 1..3:

    K0=729   table@730   k=3 : 49 / 256
    K0=1458  table@1459  k=3 : 43 / 256
    K0=2916  table@2917  k=2 : 35 / 256

`K0 = 729` is the better table but puts the table at address 730, and this
program's construction code does not fit under 730 (it ends at 1433). `K0 = 1458`
is what ships: **43/256, exact, no search**.

Only three cell-writes are input-dependent in the whole program, and every table
byte is free.

## Why this beats the branchless ceiling by so much, cheaply

`dispatch_ceiling.c` scores the general question the cov36 research was asking —
for every product partition realizable by a positionwise dispatch, the sum over
classes of that class's straight-line optimum. It grants each class its own maps
and its own constant and ignores all build cost, so it is a genuine ceiling:

                          full monoid, K free      depth-2 tail
    no split                    34                      34
    3-way on trit 3             53                      48
    3-way on trit 4             50                      49
    9-way on trits 2,3          77                      71
    9-way on trits 3,4          74                      73

So a *single* three-way dispatch on one trit already clears 40 — 48 or 49 with a
two-layer tail. cov40's threshold was never close to the branch wall; it sits
well inside the first branch's reach. The identity dispatch used here is a
different point in the same space: it takes the partition all the way to 256
classes and pays for it not in construction but in the weakness of the per-class
operand (eight legal bytes instead of an arbitrary built word). 43 is what that
trade buys, and it was the cheaper program to build.

## The program

    prefix 0..255      NOP walk; every cell holds the unique byte decoding to NOP
                       at its own address, so afterwards mem[a] = x(a) and a cell
                       with x(a) = q-1 is a ready-made "MOVD to q" pointer
                       (cov32's layout table, reused unchanged)

    CRZ 33s, CRZ 38s, CRZ 36s, ROT x4        -> mem[36] = O1 = 28795
    CRZ 34s, CRZ 35s, ROT x3, CRZ 54s,
    CRZ 56s, ROT x4                          -> mem[56] = O2 = 30253

    IN                       A = b
    MOVD 36 ; CRZ            A = crazy(b, O1)
    MOVD 56 ; CRZ            A = v = b + 1458 ; mem[56] = v
    MOVD 56                  D = 56 again
    MOVD                     D = mem[56] = v, then ++ -> b + 1459
    CRZ ; CRZ ; CRZ          A = crazy^3(v, mem[b+1459..b+1461])
    OUT ; HALT

Both operand chains come from the register-machine BFS the cov34 report
recommended (`A <- crazy(A, seed)` on a fresh cell, `A <- rot(A)` on the cell just
written), with the second leg forbidden from reusing the first leg's seed bytes
and from opening with a `ROT`. That advice was correct and saved the entire
operand-derivation problem: 7 + 11 ops, found in under a second.

The only new layout primitive is `movd_here()` — a `MOVD` emitted while `D`
already points at the cell holding `v`. Everything else is cov32's `Builder`.

## What this means for the ladder

**cov36 (rank 18) is also solved by this program** and should be re-ranked or
closed. It is not behind the wall the cov34 report placed it behind; nothing
between 34 and 43 is.

The wall is real but it is somewhere else. The ordering claim that ranks 18–21
"are one problem, not four" is now falsified on its lower half and looks likely
on its upper half: the three-way-dispatch ceilings above say cov48 (rank 20) is
reachable in principle — a 3-way split on trit 3 or 4 tops out at 48–49, exactly
at the threshold, so cov48 will have **zero slack**, the same shape of problem
cov34 had. cov64 (rank 21) needs a 9-way dispatch, whose ceiling is 71–77; that
is a construction problem with real slack, but it needs six to nine prepared
operand words and the pointer pool is the binding constraint there, not the
mathematics.

## What the next attempt should take from here

1. **The identity dispatch is free.** `crazy(crazy(b, O1), O2) = b + K0` for
   operands whose low trits are all 1 is a two-instruction way to turn the input
   into a data pointer. Any coverage rung above 34 should start here rather than
   with per-class operand construction.
2. **The program's own bytes are a lookup table.** Eight legal values per cell is
   weak but free, and because the sharing between consecutive inputs is a
   three-wide chain, the optimum over the entire table is an exact DP, not a
   search. `table_dp.c` runs in milliseconds.
3. **The unexploited axis is the table offset.** `K0 = 729` scores 49/256 —
   enough for cov48 — and the only thing blocking it is that the operand
   construction code does not fit under address 730. Shrinking that code (the
   `MOVD`-residue padding dominates: 1433 bytes for 22 instructions) is a pure
   layout problem, and it is the single highest-value thing to try next on this
   ladder.
4. **`dispatch_ceiling.c` is the map.** It scores every realizable product
   partition against this transform. Read the number before building anything.
