## What was already known, and the bug in it

The cov34 attempt proved that **34/256 is the exact ceiling of the branchless
CRAZY/ROTATE family**. The cov40 attempt then found the right architecture — a
256-entry table indexed by the input itself, reached by a MOVD on the cell the
dispatch CRAZY wrote — built it, and **solved cov40 at 43/256**. Everything
structural here is theirs. It stopped one rung short of this one, and its own
"what next" names the reason: it read `K0 = 1458, k = 3` as scoring 48 and
`K0 = 729, k = 3` as 49, so it concluded the route to cov48 was a *layout*
problem — shrink 1717 bytes of MOVD padding to fit the code under address 730.

That reading is off, and the cause is in `research/cov40/table_dp.c`. Its `legal()` returns

    33 + ((op + 33 - a) mod 94)

but the loader (`crates/classic_malbolge/src/lib.rs`, `instruction_code`, and
`crates/harness/src/dispatch.rs::source_byte_for_op`) requires
`(byte + address) mod 94` to be one of `{4,5,23,39,40,62,68,81}` with
`byte` in `33..=126`, so the legal byte is `((op - a) mod 94)` bumped by `+94`
when it lands under 33. The two disagree at every address — by 28 or by 66 —
so the entire table alphabet the DP was optimising over was fictitious. The
shipped cov40 program scores 43/256, not the 48 its DP row predicted — the gap
is exactly this. Chasing the layout problem to reach `K0 = 729` would have
landed on 49/256, a cov48 solve by one case; the corrected DP says so too, which
is why that particular row survived the bug intact. But it is a much harder
build than the one below, for six fewer cases than are actually available.

`research/cov48/table_dp2.c` is the same DP with the loader rule taken from the
VM source, and extended from `k <= 3` layers to `k <= 6`:

    K0=729   k=1..6 :   6  15  49  36  62  39
    K0=1458  k=1..6 :   6  13  43  34  62  39
    K0=2187  k=1..6 :   2  27  23  47  27  53
    K0=2916  k=1..6 :   3  35  30  65  47  71
    K0=3645  k=1..6 :   2  32  36  65  42  67

The maximum is **71/256 at K0 = 2916 with six table layers** — 23 clear of this
rung's threshold and 7 clear of cov64's. cov40 measured only `k <= 3`, where the best row is 49. Depth is not monotone —
`k = 4` at `K0 = 2916` is 65, `k = 5` drops to 47, `k = 6` is 71 — so nothing
visible at `k <= 3` suggests how much is sitting two layers further out. Six
table layers is six more CRAZY instructions and five more table bytes. It is the
cheapest possible change to that program.

## The architecture, and why it is only eleven ops of setup

    prefix of NOPs      C walks 0..255 enciphering each cell to x(a), so cell a
                        is a ready-made "MOVD to x(a)+1" pointer  (cov32's trick)
    CRZ 41, ROT 41 x4               -> mem[41] = W1 = 32440
    CRZ 43, CRZ 63, ROT 63 x4       -> mem[63] = W2 = 6196
    IN                              A = b
    CRZ 41, CRZ 63                  A = b + 2916, parked in cell 63
    MOVD on cell 63                 D = mem[63] + 1 = b + 2917
    CRZ x6                          A = crazy^6(b+2916, mem[b+2917 .. b+2922])
    OUT, HALT

The dispatch pair is forced, and the derivation is short enough to state:

- **Trits 0..5 must come through unchanged**, so `M[w2] o M[w1] = id` there.
  Only `M1 = (1,0,2)` is injective among the three rows, and `M1 o M1 = id`, so
  `w1 = w2 = 1` at every low position. That also fixes the dispatch as
  `v = b + K0` with `K0` a multiple of 729 — and `K0*1 + 256 <= 4095` caps the
  usable offsets at `729..3645`.
- **High trits** contribute `M[w2_i][M[w1_i][0]]`. For `K0 = 2916 = 4*729` the
  trits at positions 6..9 are `(1,1,0,0)`, and value 1 is only reachable as
  `M2(M2(0)) = M2(2) = 1`, so `w1 = w2 = 2` at positions 6 and 7 — forced.

`chain2.c` then runs cov34's register-machine BFS (`A <- crazy(A, x(q))` on a
fresh cell, `A <- rot(A)` on the cell just written) and finds `W1 = 32440`
in five ops and `W2 = 6196` in six more, with no seed reuse. One correction to
cov34's chain search was needed: the shortest leg-2 path is length **zero**
(`W2 = W1 = 32440` satisfies the constraints), which is a mirage — the first
CRAZY overwrites `W1`'s cell with the accumulator, so the second operand must
live in a different cell. `bfs2()` seeds the second leg at depth 1 from every
fresh-cell CRAZY successor instead of at `W1` itself.

The MOVD is the whole branch. Because `crazy` writes `A` back into `mem[d]`, the
second dispatch CRAZY leaves `v = b + 2916` sitting in cell 63; a MOVD on cell 63
sets `d = v` and the post-instruction increment makes it `v + 1`. D then walks
`v+1 .. v+6` on its own as the six CRAZYs execute, because D increments every
step. **No per-input jump table, no lane construction, no pointer pool** — the
input is the index, and the "table" is 261 bytes of the program that C never
reaches.

Each table address admits exactly eight loader-valid bytes. Consecutive inputs
share five of their six cells, so the choices are coupled along one chain and the
exact optimum over all 8^261 tables is a transfer-matrix DP on 8^5 states;
`table_solve.c` runs it with a prefix-sharing DFS over the 8^6 operand
combinations per cell and emits the winning byte for every address.

## What this leaves for the next attempt

- **Ranks 18–21 collapse.** cov40 already showed the branching wall is not one
  wall; this shows the whole run above it is not four rungs. A single program
  clears cov36, cov40, cov48 and cov64. The remaining coverage question is where
  the *table* architecture's own ceiling is, which is a different and sharper
  question than "does branching exist."
- **The ceiling of this architecture is not yet known.** 71 is the exact optimum
  over `k <= 6` and `K0` a multiple of 729 with the dispatch forced to identity.
  Three untried directions, in the order I would spend budget on them:
  `k = 7..10` (the DP is 8^(k-1) states — `k = 7` is 262k states and still
  cheap, `k = 9` is not); a **non-identity dispatch**, where the low trits go
  through a non-injective map so several inputs share a table row and the freed
  address range buys depth; and an extra fixed CRAZY *between* the park and the
  MOVD, which changes `A` without changing `D` and adds a free positionwise map
  to the DP's initial state.
- **Reusable, and cheap:** the whole build is 11 setup ops plus 12 instructions.
  Anything on this VM that needs 256-way input dependence should reach for
  "park `b + K0` with two CRAZYs whose low trits are `M1`, then MOVD on the cell
  the second CRAZY wrote" before it reaches for lanes. The lane/pointer-pool
  architecture that stalled at 27/256 on cov36 and "runs out near 30 lanes" is
  solving a problem this does not have.
- **Check the alphabet against the VM source, not against a prior attempt.** The
  cov40 DP is structurally right and numerically wrong for one off-by-33. That
  error did not cost it its solve — it verified natively, as it should — but it
  pointed the next step at a hard layout search for 49 when a two-instruction
  change was worth 71. A DP whose numbers cannot be reconciled against the
  program that came out of it is telling you something; cov40's 43 against a
  predicted 48 was the tell.
