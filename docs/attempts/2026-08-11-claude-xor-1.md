## One epoch is not definitive on this rung

`crates/harness/src/challenge.rs` derives Transform-family inputs from the epoch
seed, so the single case is a **different random byte every epoch**. A program
correct on `n` of 256 inputs passes an epoch with probability `n/256`. The only
honest measurement is all 256 bytes through `execute`; that is what the 68 below
is. `verify` on epoch 0 fails (`expected ff, got 67`).

## What the 256-byte cap actually removes

The sibling rung `L2.R0d.xor-1-len4096` is this task with `max_program_len`
relaxed 256 → 4096. That relaxation is what buys the **stride-9 private-block**
layout: rotate the cell holding `b` left two trits so each input dispatches to
its own 9-cell block and no operand cell is shared. That program is 2310 bytes.
At 256 bytes it does not exist — `9·255 + 7 = 2302` cells of table are
unaffordable — and neither is any stride > 1, for a reason that is worth
recording separately:

> **`MOVD` cannot reach past address 127.** `MOVD` does `D = m[D]` (then the
> post-increment), and every *program* cell holds a byte in `33..126`. So one
> hop lands at most on 127, and chaining hops does not help: the second hop
> reads another byte cell. Any dispatch target that is a designed program cell
> is confined to `1..127`. Only crazy-fill cells (address ≥ program length) hold
> words above 126, and those are not designable.

So this rung forces **stride 1**: `D = b + K0` and the operand table lives
inside the program at addresses `b+K0 .. b+K0+k-1`. Adjacent inputs share
operand cells. That sharing, not the byte budget, is the thing to measure.

## The layout

    0        IN            A = b
    1,2,3    MOVD x3       D: 1 -> 40 -> 123 -> 71
    4,5      CRZ x2        m[71] = m[72] = 121 = 11111_3
    6,7,8    MOVD x3       D: 73 -> 62 -> 72 -> m[72]+1 = b+1
    9..      NOP x (K0-1)  free dispatch offset (every instruction increments D)
    ..       CRZ x k       operands m[b+K0 .. b+K0+k-1]
    P-2,P-1  OUT, HALT

The parking trick is forced and worth stating exactly. `crazy` is trit-local
with `M0 = (0→1,1→0,2→0)`, `M1 = (0→1,1→0,2→2)`, `M2 = (0→2,1→2,2→1)`. Only
`M1` is a permutation, and it is the transposition `(0 1)`, so `M1∘M1` is the
only identity available: the parking operand must be all-ones,
`W = 1111111111₃ = 29524`, i.e. **two** `CRZ`s against cells holding `121` at
trits 0..4, and cell 72 then holds `b` exactly. There is no one-instruction
park.

The `NOP`-run offset is free (1 byte each) because every instruction
post-increments `D` — that is what makes `K0` a searchable parameter rather than
a rebuild.

## The exact DP, and the number

`dpk.c` is a transfer-matrix DP over addresses. Each free cell has exactly 8
loader-legal bytes; the state is the choice made for the last `k-1` cells, so
the sharing between adjacent inputs is resolved *exactly*, not sampled. Cells
`0..P-1` are code (already enciphered when the chain reads them, and *written*
by the chain, which corrupts any instruction not yet executed), cells 71/72 are
input-dependent, cells 40/62/73/123 are pinned pointer constants, everything
else is free, and cells ≥ 256 are the crazy fill.

Sweep over `k ∈ {3,5,7}` and `K0 ∈ 1..24` (72 exact optimisations):

    k=3:  best 63/256 (K0=2)
    k=5:  best 68/256 (K0=1)      <- shipped
    k=7:  best 68/256 (K0=21)

Against an idealised layout with **no** code cells and no pinned cells at all
(`dp.c`, `P=1` — a program that costs nothing, which is not buildable):

    k:      2    3    4    5    6    7
    best:  23   60   35   77   37   75

Two things fall out. **Odd `k` beats even `k` by ~2x**, which is the len4096
report's Barrier 1 showing up here: all operands are `< 243 = 3^5`, so trits
5..9 evolve under `M0` with no choice, `M0` is 2-periodic, and the forced high
word `H` is `121` at odd depth and `0` at even depth. `OUT` emits `A mod 256`,
so `L = (b⊕0x51 − 243·H) mod 256` is uniquely determined and must land in
`0..242`; the two parities kill different 13-input sets, and the odd-parity one
happens to sit better against this target. **Depth is not the lever**: `k=7`
does not beat `k=5`, because a longer window shares more cells with more
neighbours, and the sharing loss cancels the reachability gain.

The shipped program is `k=5, K0=1`: **68/256**, 256 bytes, 16 steps. The model
VM and the native VM agree on the passing set **byte for byte**, which is what
makes the ceiling a measured fact about the VM rather than a claim about my
simulator.

## The calibration result

The `len4096` record closes with: *"Relaxing the length further would not move
this rung; ranking it apart from `L2.R0.xor-1` on length grounds is measuring
the wrong variable."* On this evidence that is half right, and the half that is
wrong matters for ranking:

| | best exact, this family | architecture |
|---|---|---|
| `L2.R0d.xor-1-len4096` | **119/256** | stride 9, private blocks, 2310 bytes |
| `L2.R0.xor-1` (here) | **68/256** | stride 1, shared table, 256 bytes |
| ditto, free layout bound | **77/256** | stride 1, zero-cost code |

The length cap **is** binding — it is worth ~51 inputs, because it is exactly
what separates private operand cells from shared ones. The two rungs are not
the same difficulty and the board is right to separate them. What the `len4096`
record got right is the part that decides both: **neither** reaches 256, and
they fail for the *same* arithmetic reason. Length moves the ceiling from 68 to
119; it does not move it to 256. So the ordering `L2.R0d` (25) before `L2.R0`
(26) is correct in sign and probably understated in size — this rung is a
strictly harder instance of a task whose easier instance is also unsolved.

## What I would try next

The escape is unchanged from the `len4096` record and is now *more* forced,
because stride 1 removes the private-block freedom that made brute reachability
worth anything:

1. **`ROT` inside the walk.** Every barrier comes from operands being `< 243`.
   `ROT` at `D` does `m[D] = rotr(m[D]); A = m[D]`, promoting a controllable low
   trit to trit 9 in one instruction. Here it is cheaper than at stride 9: the
   re-entry pointer `m[72]` still holds `b`, so `MOVD` back into the table is
   three instructions and costs zero table cells. Model it first — the state is
   the full 10-trit accumulator, 59049 states, a trivial BFS — and only build if
   the model clears 256/256.
2. **Two-phase table.** With 256 bytes there are ~240 free cells but 256 inputs,
   so the table is *over-subscribed* even before sharing. A `JMP` off a table
   cell into one of eight tails would let different inputs run different depths
   (the parity flip is worth the other 13-input dead set). At stride 9 the exact
   union over depths was 194/256; the stride-1 analogue is computable in the
   same DP by adding a per-input depth axis, and is the right next measurement
   because it bounds *everything* buildable without `ROT`.
3. **Deliberately shorten the program** so more inputs read crazy-fill cells,
   which exceed 242 and break Barrier 1 outright. `dpk.c` already models the
   fill tail; sweeping `L` from 256 down to ~180 is one loop and would say
   whether undesignable-but-large operands beat designable-but-small ones. My
   sweep held `L = 256` throughout and this is the cheapest unturned stone.
