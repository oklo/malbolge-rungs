## Situation on arrival

program scores 71, and both PASS this rung. Re-running a shipped program is not
an attempt, so the question worth answering here was not "can this be cleared"
but **"is there anything left in the dispatch architecture that the two attempts
above it did not use?"** There is exactly one thing, and this rung is the natural
place to measure it, because it is the only coverage rung whose threshold sits in
the range where the cheap version of the mechanism lives.

## The unused degree of freedom: the dispatch permutation

Both prior programs use a **two**-CRAZY-layer dispatch. That choice is not
neutral. For the input to survive into the table index, the composed map on
trits 0..5 must be injective, and among the three rows

    M0 = (1,0,0)   M1 = (1,0,2)   M2 = (2,2,1)

only `M1` is injective, with `M1 o M1 = id`. So a two-layer dispatch forces the
low map to be the **identity**: `index(b) = b + K0`, `K0` a multiple of 729, and
the 256 used table cells are 256 *consecutive* cells. Consecutive inputs then
share `k-1` of their `k` cells — the maximum sharing possible — and that sharing
is precisely what the table DP has to fight, since each cell has only eight
source-legal values.

With **three** layers the picture changes. A product of three rows is injective
only if every factor is (`M0`/`M2` are not injective and non-injectivity is
absorbing), so all three must be `M1`, and `M1 o M1 o M1 = M1`. The low map is
therefore forced to be `M1` itself:

    index(b) = pi(b) + K0,   pi = trit-wise (0->1, 1->0, 2->2) on trits 0..5

`pi` is still a bijection — the dispatch is still lossless — but it is **not
order-preserving**. On the 256 inputs it spreads `pi(b)` over `109..485`, a
377-wide window holding 256 used cells instead of 256 cells packed end to end.
Roughly a third of the coupling disappears, and the DP optimum moves.

That is the whole idea: *the dispatch index map has one free parameter beyond the
offset, and it is worth points at fixed table depth.*

## Measuring it

`research/cov36/perm_dp.c` is the exact transfer-matrix DP over the table, with
the loader's legal-byte rule (`(byte + a) mod 94 in {4,5,23,39,40,62,68,81}`,
`byte` bumped by +94 when it lands under 33 — the rule cov40's DP got wrong and
cov48 corrected), run for both index maps, every reachable offset and depths
`k = 1..6`. State is the last `k-1` cell choices; at most one input ends its
window at any cell because the index is injective, which is what keeps the DP
exact under a permuted index too.

    pi=id  (2-layer)  K0=0     :   18   23   60   35   77   37
    pi=id  (2-layer)  K0=729   :    6   15   49   36   62   39
    pi=id  (2-layer)  K0=1458  :    6   13   43   34   62   39
    pi=id  (2-layer)  K0=2187  :    2   27   23   47   27   53
    pi=id  (2-layer)  K0=2916  :    3   35   30   65   47   71
    pi=id  (2-layer)  K0=3645  :    2   32   36   65   42   67
    pi=M1  (3-layer)  K0=0     :    3   35   32   76   38   78
    pi=M1  (3-layer)  K0=729   :    1   36   32   58   46   70
    pi=M1  (3-layer)  K0=1458  :    3   34   35   62   41   68
    pi=M1  (3-layer)  K0=2187  :    5   24   51   44   65   54
    pi=M1  (3-layer)  K0=2916  :    3    7   42   28   56   32
                                    k=1  k=2  k=3  k=4  k=5  k=6

The `pi=id` rows for `K0 = 729..3645` reproduce `research/cov48/table_dp2.c`
exactly, which is the check that this DP is the same DP.

Two things fall out.

- **The permutation is worth real points at fixed depth.** At `k=3`, `K0=2187`:
  23 → 51. At `k=4`, `K0=0`: 65 (best id row) → 76. It is not uniformly better —
  at `K0=2916` it is much worse — because it is a *different* sharing pattern,
  not a looser one. It is a second axis to optimise over, and it roughly doubles
  the configuration space that was being searched.
- **cov36's threshold is exactly where this axis first matters.** No two-layer
  dispatch with a two-cell tail reaches 36 at any offset — the `k=2` column of
  the `pi=id` block tops out at 35. The permuting dispatch at `K0=729, k=2`
  scores **exactly 36**. So the cheapest possible tail on this architecture
  clears this rung and only this rung, and it needs the permutation to do it.

## What shipped, and why not the 36

The `K0=729, k=2` configuration puts the table at addresses 839..1216, so the
whole setup must fit under address 839. The layout in `build36.py` — cov32's
prefix-of-NOPs pointer table, unchanged — produces 807 bytes of code for 21
`MOVD`-addressed instructions, ending at 1063. It does not fit, and shrinking it
is the same `MOVD`-residue padding problem cov40 already flagged as the open
layout question on this ladder. Under a 25-minute cap that was not the right
thing to spend the remaining time on.

What ships is the same mechanism at the offset with room: `pi = M1`,
`K0 = 2187`, `k = 3` → **51/256**, table at 2297..2675, code ending at 1063.

    prefix 0..255       NOP walk; cell a ends up holding x(a), so a cell with
                        x(a) = q-1 is a ready-made "MOVD to q" pointer

    13 ops              -> mem[W1] = O1 = 29524
                           mem[W2] = O2 = 56497   (chained from O1, no reset)
                           mem[W3] = O3 = 2551    (chained from O2)
    IN                       A = b
    MOVD W1 ; CRZ            A = crazy(b, O1)
    MOVD W2 ; CRZ            A = crazy(., O2)
    MOVD W3 ; CRZ            A = v = pi(b) + 2187 ; mem[W3] = v
    MOVD W3 ; MOVD           D = mem[W3] = v, then ++ -> v+1
    CRZ ; CRZ ; CRZ          A = crazy^3(v, mem[v+1 .. v+3])
    OUT ; HALT

The three operand words come from cov34's register-machine BFS
(`A <- crazy(A, x(q))` on a fresh cell, `A <- rot(A)` on the cell just written),
run as three chained legs — leg `n+1` starts from leg `n`'s parked value and may
not open with a `ROT`. One correction to the inherited search: seeds must be
distinct **within** a leg as well as across legs, since every CRAZY consumes the
cell it reads and `x(.)` is injective on 34..127. cov40's builder only enforced
it across legs and happened not to hit the case; the three-leg search hits it
immediately (`build36.py:distinct`). Chain lengths 1 + 6 + 6.

## For the next agent on this ladder

1. **Search the index map, not just the offset.** Two layers give `id`, three
   give `M1`; both are free choices of the dispatch, and at fixed depth they
   differ by up to +21. Nothing above `k=6` or beyond three layers was measured —
   four layers give `M1 o M1 = id` again, so the axis is exactly two-valued, but
   the offsets and depths crossed with it are not exhausted (`K0=0` is unscored
   for buildability reasons, see below, and it holds the two largest numbers in
   the table: 77 at `pi=id, k=5` and 78 at `pi=M1, k=6`).
2. **`K0 = 0` is the prize and it is a layout problem.** With `K0=0` the table
   sits at 110..487 (`pi=M1`) or 1..262 (`pi=id`) — inside or just past the
   prefix, i.e. in cells the program executes or uses as its pointer table.
   Whoever solves *that* gets 77–78/256, which clears cov64 with room. It needs a
   construction that does not depend on cov32's prefix trick, or a prefix whose
   bytes double as table entries.
3. **The `MOVD`-padding cost is still the binding constraint**, exactly as cov40
   said: 21 instructions cost 807 bytes here, ~38 bytes of NOP per instruction,
   and that is the only reason the exact-36, two-cell-tail program could not be
   built. Any halving of it opens `K0=729` at every depth.
